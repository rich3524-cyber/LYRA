# Step 1B — Architecture & Design Review (raw agent output)

Two sub-reports from the `architect-review` agent: a top-level architecture review, and a dedicated data-model / cross-cutting debt pass it split off on its own.

---

## 1. Top-level Architecture & Structural Integrity Review

**Surveyed:** 82 API route files (7,312 LOC), 29 pages, 104 components, 68 service files, 13 workers, 33 lib modules, 28 Prisma models / 16 enums, 49 test files.

**Executive summary:** LYRA's architecture is not short of good ideas — `services/social/provider/` is a textbook Strategy pattern, `services/notifications/` is a clean vertical slice, `lib/anthropic.ts`/`safe-fetch.ts`/`encrypt.ts`/`oauth-state.ts`/`validate.ts` are all well-designed. **The defining problem is that abstractions get created but not adopted** — `canWrite()` is called at 12 of ~72 sites it should govern; `lib/queues.ts` warns against declaring queues elsewhere and two queues do; `lib/plan-access.ts` was built to stop paid-feature drift and the one route that flips that feature doesn't import it.

The deeper structural cause: **`services/` is not the domain layer it's named as.** 113 of 130 `@/lib/prisma` imports live in `app/` (92 in routes, 21 in pages); `services/` holds only side-effect adapters. There's no place for a business rule to live, so business rules live in HTTP handlers, where the only way to reuse one is to copy it.

### CRITICAL

- **C1 — The post lifecycle state machine has four implementations and no owner.** `posts/[id]/route.ts`, `posts/route.ts`, `bulk-import/commit/route.ts`, and `post-detail-panel.tsx`'s `getNextStatuses` each independently encode approval routing/self-approval/status transitions. Code comments across all four explicitly record divergences found and fixed after shipping (the self-approval deadlock fix had to land in two files; the missing-`PostApproval`-row bug was fixed twice in two sessions because the second copy wasn't known about). Fix: `services/posts/post-lifecycle.ts` as single owner (`resolveCreateStatus`, `resolveTransition`, `allowedTransitions` all built on one table), consumed by all four sites.
- **C2 — Multi-tenant authorization has no shared primitive.** Two incompatible idioms across 65 route files + 16 pages, with no helper: one does a separate lookup and returns 403 on miss (25 files), the other inlines a nested Prisma filter and returns 404 on miss (40 files) — **the identical failure returns two different status codes depending which file you're in.** Role policy has 4 separate vocabularies (`canWrite`, `APPROVER_ROLES`, `OWNER_ROLES` redeclared in 6 files with 2 different type signatures, and one inline ad-hoc role list at `onboarding/route.ts:25` that excludes `SMB_OWNER`/`PLATFORM_OWNER` for no stated reason). **36 of ~72 mutating routes apply no role check at all** — including `posts/[id]/boost` (real ad spend), `comments/[id]/reply` (posts publicly as the brand). Live gap found: `app/api/seo/connect/route.ts:10-16` calls `requireAuth()` but does **zero tenancy check** before starting an OAuth flow naming an arbitrary workspace — any authenticated user can initiate this for any workspace in the system (contained only because the callback re-checks). Fix: one `requireWorkspace(userId, workspaceId, policy)` helper + a route-manifest test enumerating exemptions.
- **C3 — `services/` is not the domain layer; `app/` is.** 113/130 Prisma imports live in the route/page layer. Named routes carrying 60+ lines of untested domain logic with nowhere else to live: `mcp/respond-to-item` (299 LOC), `posts/[id]` (280), `posts/route` (243), `social/callback/[platform]` (239), `stripe/webhook` (238), `comments/[id]/reply` (209), `analytics/route` (161), `zernio/webhook` (194). None has a true unit test — all are HTTP-level tests with mocked Prisma. `services/posts/bulk-import.ts` is offered as the internal model to copy: pure, DI'd, 231 lines of tests, zero HTTP knowledge.

### HIGH

- **H1 — Entitlement layer remains bypassable; the fix exists and is unimported.** `lib/plan-access.ts`'s `hasCrisisAwareAccess()` is correctly used in 2 routes but NOT in `workspaces/[id]/route.ts` — the one route that actually flips the paid `crisisAware` flag, which still uses a hand-written `plan === 'STARTER'` check. A PRO workspace with no Crisis Aware subscription gets the add-on free. This is the *same* bug the 2026-08-02 review reported; the fix built in response was never wired into the route that needed it. Live revenue leak.
- **H2 — `POST /api/posts/[id]/publish` is the one publish path with no atomic claim.** The worker and the MCP respond-to-item route both use a status-scoped `updateMany` compare-and-swap claim before any external call; this manual "Publish now" route does a plain read-then-write, so a race with the cron can double-publish, and its unconditional final `update` can clobber a `FAILED` status the worker's failure handler just wrote.
- **H3 — Schema and database have three sources of truth, one already drifted.** The 2026-08-02 baseline migration was never marked applied (`DIRECT_URL` unreachable from dev machine); 8 hand-applied files sit outside Prisma's ledger; and `schema.prisma`'s `NotificationChannel.workspace` relation has no `onDelete` (defaults to Restrict) while the actual hand-applied SQL used `ON DELETE CASCADE` — the generated client and live DB genuinely disagree, undetectable by `prisma migrate diff`.
- **H4 — Referential integrity enforced in application code, and the ladders are already incomplete.** Only 11/30 relations declare `onDelete`; the rest default to Restrict, forcing two hand-written cascade-delete transactions (workspace, account) that are **missing 9 tables** and survive only by accident (those relations happen to carry Cascade the code doesn't know about). `Comment.workspaceId` — the most security-critical column in the schema — has **no foreign key at all**. `FacebookPending.workspaceId` likewise unconstrained. `CrisisEvent.commentIds` is an unconstrained string array of comment ids. 4 tables (`PostApproval`, `PostMetrics`, `PostBoost`, `CommentResponse`) carry no tenant column at all, reachable only by join. Zero Postgres RLS anywhere — isolation is 100% application-level.
- **H5 — `SocialProvider` abstraction covers half its domain; the other half is a 7-way fork.** Publish logic splits with no consistent rule (Facebook delegates properly, Instagram/LinkedIn/Twitter are hand-rolled private functions inside the "abstraction" file). OAuth has no interface at all — 6 near-identical `getAuthUrl`/`exchangeCode` copies force a 7x `import *` fan-out in the callback route (239-line branch, highest fan-out file in the repo). `zernioClient` is bypassed directly by 7 files that should route through `getProvider()`. Comment ingestion bypasses the provider entirely in 2 places, independently, and has already drifted on the self-comment filter.
- **H6 — No error taxonomy, no dead-letter queue, no alerting.** Zero hits for Sentry/DLQ/`captureException` anywhere. Only one place distinguishes permanent vs. transient failure. Everything else retries a revoked-token failure identically to a transient 500, burning attempts indefinitely with only a per-post `failureReason` string as the customer-visible signal — even though the machinery to auto-deactivate a dead account already exists and is simply never reached from worker-side failures.
- **H7 — Posts stranded in `PUBLISHING` have no reconciler.** No sweep exists anywhere for a post stuck mid-publish (all retries exhausted, shutdown-drain timeout, or a crash — one of which occurred in production per commit `190a253`). Silently never published, never marked failed.
- **H8 — Analytics computed twice, from different columns, can disagree for the same customer on the same period.** `analytics/route.ts` and `reports/generate/route.ts` independently hand-aggregate the same `PostMetrics` rows using **different metric field sets**. The same analytics page even reports two different comment totals from two different source paths that will never agree.
- **H9 — `Json` columns have no shared types.** `BrandProfile.postingPatterns` alone has 5 read/write sites assuming 4 different shapes, no schema, and 8 total `JSON.parse(JSON.stringify(...))` round-trips purely to satisfy Prisma's `InputJsonValue` type — a symptom of the missing schema, not a real serialization need.
- **H10 — Missing indexes on the hottest query shapes**, most notably `Post @@index([workspaceId, createdAt])` (used by the workspace overview, `take:200` post list, and brand-intelligence build) and `WorkspaceAccess @@index([workspaceId])` (its only 2 indexes both lead with `userId`, so the crisis-alert-email path does a full cross-tenant table scan of every access grant during an active crisis).
- **H11 — Three competing scheduler declarations.** `vercel.json` still declares 3 (now-wrong) crons; `Dockerfile.worker` is documented-unused; only Railway cron is real (per this session's own migration work). `cron/sync-trends` is the only cron route missing `checkCronAuth` entirely — harmless today only because it returns a static literal.

### MEDIUM (M1–M10) — summarized

Five incompatible API error response shapes coexisting (M1); zod validation adopted at only 6/~50 body handlers, 5 handlers do *zero* body validation (M2); Prisma types leak into React in 7 files, including a genuine (currently safe only via `import type`) 4-node import cycle between a route file and 3 components (M3); no shared frontend API client — 67 raw `fetch()` calls, each re-typing the response shape inline (M4); 2 queues declared outside the documented single registry, one of which is an import-side-effect landmine inside a worker file (M5); the worker-build tsconfig pulls `next/headers` into the compiled worker output via an incomplete exclude list (M6); a multi-platform post has no aggregate root — N independent `Post` rows per composition with no `postGroupId` (M7); `post-detail-panel.tsx` (671 lines, up from 606) and `post-composer.tsx` (539, up from 489) both grew since the last review, tangling unrelated concerns including a full paid ad-boost purchase flow (M8); rate limiting present on 23/82 routes but gappy and inconsistently calibrated — several expensive/spend-real-money routes remain unlimited (M9); dead surface area — 3 of 4 upload routes have no caller, the entire `Review` model has zero call sites despite being fully implemented end-to-end including tests for its (dead) mapper, several empty scaffold directories (M10).

### What's genuinely improved since 2026-08-02

Migration baseline now exists with honest documentation; `platform-labels.ts` consolidated ~9 duplicate files; workspace plan limits now enforced; `checkCronAuth` consolidated and made timing-safe; publisher worker has a real compare-and-swap claim; graceful shutdown added; 4 new `Post` indexes; rate limiting went from 3 routes to 23; `EmailIntegration.apiKey` now encrypted with a migration path; a placeholder-image-could-publish-live bug removed.

### Recommended sequence (from this sub-report)

Before beta: H1 (wire the entitlement check, one import), H2 (atomic claim, ~5 lines), C2-partial (fix `seo/connect`'s missing tenancy check + role-gate the money/publish routes), H3 (run the migration resolve), H11 (delete the 3 stale scheduler files). Next quarter: C1, C2-full, H8, H4, H10, H6. Ongoing: C3 (extract by domain as each area is next touched), M1/M2.

## 2. Data Model & Cross-Cutting Architecture (split-off sub-report)

**Headline:** materially better shape than its size suggests — multi-tenancy is genuinely consistent (211 tenant-scoped Prisma calls audited; zero unscoped queries found), zero `as any` in production code, zero `@ts-ignore`, zero TODO/FIXME, `tsc --noEmit` passes clean. Debt concentrates in three places: no validated config layer, an anaemic service layer, and a schema that has drifted from the live database — one of which produced a **live, verified billing defect**.

### CRITICAL

- **A1 — `Agency.plan` defaults to `AGENCY` (the most expensive tier)**, while `Workspace.plan` correctly defaults to `STARTER` — the two entitlement columns fail in opposite directions. Any `Agency` row created before its Stripe webhook resolves (confirmed: `app/onboard/page.tsx:33-38` creates one with only `name`+`members`) is fully entitled to the top plan by default. This is the amplifier that turns B1 (below) from cosmetic into a real revenue loss.
- **B1 — `/onboard?plan=<anything>` charges the wrong price and grants the wrong entitlement — traced and verified end to end.** `?plan=enterprise` (or any unrecognized value): the page falls back to charging the **Pro** price (`?? 'PRO'`), but writes the **raw unresolved param** (`'enterprise'`) into Stripe checkout metadata rather than the resolved plan key. The webhook's `toPlan('enterprise')` correctly returns `undefined` (a deliberate fix for an earlier billing bug), so the plan update is skipped — leaving the agency on its **default** (`AGENCY`, per A1). Net effect: **customer is charged the Pro price and keeps Agency-tier entitlements**, with the only trace being one unlogged-by-default console line. The query param is user-editable in the browser address bar. A secondary bug in the same file: the platform-lookup object is a plain literal, so `?plan=constructor` throws a 500 from a bare query string.

### HIGH

- **A2 — Schema and live database disagree on a real referential action, confirmed by direct SQL audit** (not the same speculative gap H3 above flagged — this one is verified): `schema.prisma`'s `NotificationChannel.workspace` relation has no `onDelete` (→ Restrict), but the actual hand-applied migration SQL that created the table used `CASCADE`. Workspace deletion works *today* only because of the live CASCADE the schema file doesn't know about; the moment anyone runs `prisma migrate dev` from the schema file in a fresh environment, deletion breaks there specifically.
- **A3 — Account deletion 500s for any user who authored a post in a workspace they don't own.** The live FK is `Post.authorId → User, ON DELETE RESTRICT`. The account-deletion route only deletes posts in workspaces the user *owns*, but any role passing `canWrite` (not just owners) can author a post per `posts/route.ts`. A departed team member's posts in someone else's workspace survive deletion and abort the whole transaction with a 500 — the GDPR "delete my account" path is broken for exactly the multi-person-workspace case.
- **A4 — `prisma/schema.sql` is a loaded gun**: 3 months stale, contains only 13 of the current 28 tables, and its first executable line is `DROP TABLE ... CASCADE`. Not referenced by any script or CI step — pure hazard, sitting in the repo with an instruction comment to run it in the Supabase SQL Editor.
- **B2 — No validated config module: 64 non-null `!` assertions and 21 unguarded template-literal env interpolations.** The dangerous pattern is the interpolation, not the fallback — `${process.env.APP_BASE_URL}/onboard/${token}` silently renders as the literal string `"undefined/onboard/abc123"` and is returned with **HTTP 200** as a real onboarding link. Same shape in Stripe checkout URLs and 12 OAuth `redirect_uri` sites. Three incompatible per-module strategies exist (throw / silent localhost fallback / log-and-return). Confirmed as a live, currently-occurring bug: `KLAVIYO_PRIVATE_API_KEY`/`KLAVIYO_LIST_ID` are absent from both `.env.example` and `.env.local` — **every paying signup is currently being silently dropped from the marketing list**, with only a swallowed console.error as evidence. 9 vars total are read but undocumented in `.env.example`, including the entire SEO/Search-Console feature's required config.
- **B3 — No canonical workspace-access guard; the identical Prisma predicate is hand-copied ~30 times across 28 files**, alongside 4 more one-off variant shapes. `lib/authz.ts`'s own header comment already documents the exact incident this exact duplication caused previously (role checks reaching only 4 of 66 mutating routes) — the helper was added in response, but the copy-paste pattern that allowed the gap in the first place was never addressed, so nothing prevents call site #31 from omitting the role check the same way.
- **B4 — 33 of 82 routes parse `req.json()` with zero schema validation**; `posts/[id]/boost/route.ts` (spends real ad budget) does an `as`-cast then hand-writes 4 `if` blocks re-deriving what one zod schema would declare once.
- **B5 — Comment ingestion and the reply-rollback state machine each exist 2-3 times, independently, and have already diverged with real consequences.** The ingestion duplication already caused a live, confirmed incident (2026-07-22): the worker's copy had no self-comment filter, so it re-ingested the AI's own reply as a new incoming comment and drafted a reply to itself. The rollback duplication: two copies (`comments/[id]/reply` route, `ai-responder.worker.ts`) are character-identical down to the log string; a third copy in `mcp/respond-to-item` independently dropped the retry loop *and* stopped restoring the AI draft on rollback — its own inline comment explains why that specific omission reopens a double-post risk the mechanism exists to prevent.
- **B6 — The entire billing state machine lives inside the Stripe webhook route** — 238 lines, 26 Prisma operations, 4 nested transactions, no `services/billing/` module at all. The file's own comments record two past billing incidents caused by exactly this shape. A founding-member-slot allocation (`count` then conditionally `update`, both inside one transaction) is not actually race-safe under Postgres's default isolation level, so concurrent checkouts can over-allocate past the intended 100-slot cap.

### MEDIUM (A5–A10, B7–B10) — summarized

Migration ledger is more incomplete than its own README documents — a second post-baseline table (`NotificationChannel`) has drifted in beyond the one already-acknowledged `McpAuditLog` gap (A5); 21 of 32 relations have no `onDelete`, and the predicted consequence (a new child model landing without updating both hand-written delete chains) already happened once, live (A6); `Comment.workspaceId` is the tenant-isolation key for the highest-volume table and has no FK — verified not currently exploitable given today's write paths, but structurally unenforced (A7); 3 status columns are free-text `String` where every schema peer is an enum, and one of them (`CrisisEvent.triggerType`) is hand-redeclared as a union in 4 separate files that can silently disagree (A8); `Comment` — the most state-machine-heavy table in the schema — has no `updatedAt`, making the exact class of rollback bug found in B5 harder to diagnose forensically (A9); `WorkspaceAccess` has no index usable for a workspace-only lookup, forcing a full-table scan on the crisis-alert-email path specifically (A10); services/billing extraction gap causes 5 near-identical OAuth-callback upsert blocks, one already silently missing a field the others have (B7); no structured logger anywhere, 191 raw console calls, confirmed to have already cost real debugging time on at least 2 documented incidents (B8); the same auth-catch-block duplicated in 67 files, only 5 of which also handle validation errors correctly (B9); the platform-label dedup from the last review was itself re-forked 3 times by newer files, one already missing 4 of 10 platforms and rendering the raw enum value in a customer's inbox (B10); ESLint is accidentally linting the `.netlify/` build-artifact directory, inflating the reported problem count from a real ~8-in-source to 22,713 — meaning the documented "762 pre-existing lint errors, non-blocking" CI carve-out is based on stale/wrong numbers and could likely be turned back into a blocking gate almost immediately (B11).

### LOW (A11 + misc)

An entire `Review` model — table, indexes, cascade FKs, provider-interface methods, client methods, and even a unit test for its mapper — has zero live callers anywhere; `Workspace.ownerId` has no FK/index/reader (ownership actually lives in `WorkspaceAccess.role` instead); plan limits are separately hardcoded in `lib/stripe.ts` while `Agency.maxWorkspaces`/`maxAutonomy` columns exist, are read by nothing, and would silently do nothing if an operator "fixed" a customer's limit by editing them directly.

### Testing findings (this sub-report also covered test posture directly)

Suite health is good: 49 files / 457 tests, all passing, 5.97s, zero skipped/todo tests. But:
- **C1 (Critical) — the test suite does not gate deployment.** CI runs tests correctly and marks the deploy job as depending on them, but Netlify and Railway both deploy via their own independent GitHub-integration auto-deploy, in parallel with the test job, not after it — a red test currently produces a failing check with no actual effect on what ships. No branch protection exists to close this gap (a zero-code fix: turn it on).
- **C2 (Critical) — `checkCronAuth`, the only thing protecting all 6 public cron endpoints, is completely untested**, including its fail-closed no-secret-configured branch and the length pre-check that exists specifically to keep the timing-safe comparison from throwing.
- **C3 (High) — the shared authorization and crypto primitives (`lib/authz.ts`, `lib/plan-access.ts`, `lib/encrypt.ts`) have zero tests**, despite each gating something specifically security- or revenue-critical, and despite each having an explicit comment explaining a non-obvious correctness property (fail-closed default, hex offset math) that a test would pin.
- **C4 (Medium)** — the 282 `as any` Prisma-mock casts across route tests are a standard/reasonable pattern, but they mean a schema rename would silently keep the whole route-test suite green while production breaks; suggests a typed factory-per-model fix that also happens to retire the majority of the B11 lint-count inflation.
- Test *quality* where it exists is explicitly called out as good — real dependency-injection use, real negative-assertion security tests (asserting the DB was never touched on an auth failure), not change-detector tests.
