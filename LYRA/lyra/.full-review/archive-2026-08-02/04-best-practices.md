# Phase 4: Best Practices & Standards

**Date:** 2 Aug 2026 · **Scope:** Full LYRA codebase, as defined in `00-scope.md`

---

## Framework & Language Findings

**Counts: 0 Critical · 3 High · 7 Medium · 8 Low**

### Executive summary

LYRA's TypeScript/Next.js layer is genuinely well-modernized — a noticeably stronger showing than the architecture/security phases. The Next.js 15+/16 async-request-API migration (`params`, `searchParams`, `cookies()`, `headers()`) is 100% correct across all 34 dynamic-route sites with zero legacy patterns; there is no `pages/` directory, no deprecated React APIs, zero `enum` usage, zero `as any`, zero mixed async chains. Where it falls short is underused modern capabilities and asymmetric rigor: React's `cache()` is never used, so `getCurrentUser()` — which does an Auth0 session fetch *and* a Prisma **write** — fires twice on every dashboard page load, compounding the Phase 2 connection-pool bottleneck finding. Zod validates every inbound request but never any of the ~30 outbound third-party API responses (Facebook, LinkedIn, Zernio, GSC, etc.), an inverted risk posture since those are shapes LYRA doesn't control. `noUncheckedIndexedAccess` is off, and a concrete, 9x-duplicated unsafe-indexing bug pattern reading Claude responses is exactly what it would have caught — compounding the Phase 1 "no shared Anthropic wrapper" finding. Package management has one real infrastructure risk: no `engines` field, with the worker's Node version and even its entrypoint command defined two different, inconsistent ways between `Dockerfile.worker` and `railway.toml`.

### HIGH (3 total)

- **F1** — `getCurrentUser()` (`lib/auth.ts`) is not wrapped in React's `cache()`, despite performing an Auth0 session fetch *and* a Prisma `upsert` (a write). It's called from 15 files, including both the dashboard layout and every nested page in the same render tree — meaning at minimum 2 Auth0 calls + 2 Prisma writes fire per dashboard navigation for identical data, on the single most-executed code path in the app, directly compounding the Phase 2 finding that the app and worker fleet share one `connection_limit=1` Postgres connection.
- **F2** — Zod (`lib/validate.ts`) validates every inbound client request but is never applied to the ~30 outbound third-party API response sites (Facebook, LinkedIn, TikTok, GSC, Klaviyo/Mailchimp/Customer.io, Zernio, Perplexity) — all parsed via blind `as {...}` casts. This is the inverted risk posture: a third-party shape change silently produces stored `undefined` rather than a caught error. Priority: Stripe webhook payload, Zernio webhook payload, and OAuth token-exchange responses first, since those failures are hardest to debug in production.
- **F3** — No `engines` field in `package.json`; confirmed real drift across every deploy target — local dev Node 24, `Dockerfile.worker` pins Node 20, `railway.toml`'s `startCommand` runs a *different* worker entrypoint (`tsx workers/index.ts`) than the Dockerfile's compiled `CMD`, and `netlify.toml` has no `NODE_VERSION` set. Given `bullmq`/`ioredis` are timer/event-loop sensitive, this is a concrete operational risk, and it's genuinely unclear from the repo which worker entrypoint is what actually runs in production (ties directly to Phase 4B's H3 finding that neither `Dockerfile.worker` is wired to Railway's actual build).

### MEDIUM (7 total)

`satisfies`/discriminated-union exhaustiveness checking is unused anywhere (`lib/stripe.ts`'s `PLANS` object, the Zernio webhook's untyped `event: string` discriminant); `noUncheckedIndexedAccess` is off in `tsconfig.json`, and the unsafe `response.content[0].type === 'text' ? ... : ''` pattern is duplicated across 9 separate Claude-call-site files (compounding Phase 1's H14/H16); 14+ client components fetch their own data on mount via `useEffect` instead of the Server Component + Prisma pattern every sibling route otherwise uses (`competitors/page.tsx` is a full client-rendered page where every sibling is an async Server Component); the `shadcn` CLI scaffolding tool is misplaced in `dependencies` rather than `devDependencies`, shipping it into every production install including the worker image; `puppeteer-core` + `@sparticuz/chromium-min` (a full headless-Chromium stack) is used to rasterize one static, visitor-agnostic, already-2hr-S3-cached Help PDF, duplicating the lighter `@react-pdf/renderer` already used elsewhere in the codebase; `next.config.ts` has no `serverExternalPackages` declared for native/server-only deps (`puppeteer-core`, `sharp`, `ioredis`, `bullmq`); 7 of 66 route handlers (notably `app/api/cron/sync-comments/route.ts`) have no try/catch, producing unhandled 500s with no logging context on a cron-triggered job.

### LOW (8 total)

Two removable non-null assertions where `??`/hoisting already makes them redundant; `tsconfig.json`'s `target: ES2017` is stale relative to the Node 24 runtime (low-impact since Turbopack/SWC does actual transpilation, not `tsc`); only one Server Action exists in the entire app (`disconnectAccount`), meaning React 19's `useActionState`/`useFormStatus`/`useOptimistic` are wholly unadopted despite dozens of hand-rolled `useState`-based form-loading patterns that could use them; `force-dynamic` is applied to only 41/66 routes (cosmetic — Next 15+ already defaults uncached, and cookie-reading auth calls force dynamic rendering regardless); zero `loading.tsx`/`error.tsx`/`not-found.tsx`/`generateMetadata`/`Suspense` usage anywhere in `app/`, forgoing route-level streaming/error boundaries in favor of ad hoc `useState` loading flags; a dead, unreferenced `components/lyra/marketing/marketing-page.tsx` subtree (7 files) superseded by the live `app/page.tsx`; `axios` is an unused dependency (zero import sites, all HTTP calls use native `fetch`); `typescript: ^5` has an unbounded floor with no lockfile-loss protection.

**Notably clean (zero findings, verified by exhaustive grep):** no deprecated Next.js/React APIs anywhere (`getServerSideProps`, `forwardRef`, `React.FC`, string refs, legacy Context, `useFormState`, TS `enum`) — this section of the review found nothing to flag at all.

## CI/CD & DevOps Findings

**Counts: 3 Critical · 6 High · 5 Medium · 3 Low**

### Executive summary

LYRA ships to production through a pipeline that verifies almost nothing and can fail silently at the step that matters most. CI type-checks and builds but never runs the 37-test suite that exists, and the worker-deployment job is wrapped in `continue-on-error: true` — a broken Railway deploy shows green with no alert to anyone. There is no environment isolation: `netlify.toml` has no per-context configuration, so every PR preview build runs against the same live production database, live Stripe account, and live Auth0 tenant as production itself. Infrastructure-as-code is in an advanced state of drift: two independently-committed, non-identical copies of the entire app tree, `Dockerfile.worker`, and the CI workflows exist (repo root vs. `LYRA/lyra/`), and neither `Dockerfile.worker` copy is actually used — Railway builds via Nixpacks (`buildCommand`/`startCommand` in `railway.toml`), not Docker, meaning the Critical Phase 2 finding about the Docker image running as root with the full `.env` copied in is not *currently* exploitable via the live deploy path, but remains a live landmine for the next person who touches `railway.toml`. Compounding this, CI has zero path filtering, so any commit anywhere in the user's entire OneDrive-turned-git-repo fires a full LYRA build and a live Railway worker deployment. There is no monitoring, no error tracking, no alerting, and no health-check endpoint anywhere — `console.*` (129 call sites across 73 files) is the only observability mechanism, read by nobody. No incident runbook exists.

### CRITICAL (3 total)

- **C1** — `.github/workflows/deploy.yml`'s `deploy-workers` job has `continue-on-error: true` (lines 93-108). If `railway up` fails for any reason, the GitHub Actions run still shows green on `main`; the Railway fleet keeps running the previous image while everyone believes the fix shipped. Given there's no monitoring on the worker side either (H4), this is undetectable except by a user reporting scheduled posts aren't going out.
- **C2** — `netlify.toml` has no `[context.deploy-preview]`/`[context.branch-deploy]` overrides — every PR preview build reads the exact same production `DATABASE_URL`, `STRIPE_SECRET_KEY`, `AUTH0_*` tenant, and `RESEND_API_KEY` as production itself. Any PR — including an experimental or AI-agent-authored branch — that gets a preview deploy can trigger real Stripe charges, real emails to real users, and real writes to the production Postgres instance.
- **C3** — `deploy.yml` has no `paths:` filter. The git repository root is confirmed to be the user's entire OneDrive folder, containing dozens of unrelated trees (a separate CRM/website codebase, personal documents, photos). A commit touching only an unrelated file still fires this workflow and — if on `main` — executes a live worker redeploy via `railway up`. Combined with C1's silent failure-swallowing, an irrelevant commit can silently break the live worker fleet with zero attribution trail.

### HIGH (6 total)

- **H1** — `npm test` is never invoked anywhere in CI (only `lint-and-typecheck` and `build` run) — confirms and extends Phase 3's finding from the deploy-pipeline angle: every merge to `main` (which auto-deploys via Netlify) ships without running a single automated test.
- **H2** — Two live, independently-committed, actively-drifting copies of the entire app tree, `Dockerfile.worker`, and `.github/workflows/` exist at the repo root and at `LYRA/lyra/` — `git log` confirms 79 commits against the root copy vs. 152 against the real one, and the two workflow-file copies have already diverged (the dead root copy references stale env var names). A developer editing the root-level workflow file (which "feels" like the project root) can believe they've updated live CI when they haven't touched anything real.
- **H3** — Neither `Dockerfile.worker` copy is wired to Railway's actual build: `railway.toml` uses Nixpacks-style `buildCommand`/`startCommand` fields, not `builder = "DOCKERFILE"`. The real production start command is `npx tsx workers/index.ts` — raw TypeScript via `tsx`, not the compiled `dist/` the Dockerfile produces. This independently confirms and extends the 18 Jul review's "likely broken Docker path" finding to "not wired into the deploy at all" — meaning the Phase 2 Critical (root-user container, full `.env` copied into the image) is a dormant landmine rather than a live exploit today, but activates immediately and silently the moment anyone flips `railway.toml` to the Dockerfile builder.
- **H4** — No monitoring, error tracking, or alerting anywhere in the stack (zero matches for Sentry/Datadog/pino/winston/etc.); 129 `console.*` calls across 73 files are the entirety of runtime observability, landing in ephemeral, unqueried platform logs. This is the direct enabler of C1 and H1's silent-failure risk — there is currently no way to know LYRA is degraded except a customer complaint.
- **H5** — `CRON_SECRET` is interpolated directly into a shell command string in `crons.yml` (should use `env:`) rather than a safer indirection; separately and more importantly, `publish-due-posts` — the endpoint that actually publishes every customer's scheduled content, confirmed by Phase 1 to have no in-repo trigger at all — is not present in `crons.yml` either, meaning the single most business-critical cron has zero version-controlled fallback if the external cron-job.org account is ever lost.
- **H6** — No `npm audit` gate, no CodeQL, no Dependabot, no secret scanning anywhere in CI. A direct `npm audit --omit=dev` run during this review confirmed the 14 advisories (10 High) Phase 2 flagged, including high-severity `sharp` and `undici` chains, currently flowing to production unblocked by anything in the pipeline.

### MEDIUM (5 total)

No verifiable branch protection on `main` (push-triggered CI running is not the same as CI gating a merge); no `.dockerignore` for either `Dockerfile.worker` copy (dormant, resurfaces immediately if H3's fix is applied without also adding this); no documented rollback procedure for either Netlify or Railway despite both platforms supporting one-click rollback natively; lint runs with `continue-on-error: true` due to an explicitly-documented 762-error pre-existing backlog, meaning the one nominal quality gate currently enforces nothing and new violations can be introduced indefinitely; `README.md` is confirmed unmodified `create-next-app` boilerplate that actively tells new contributors to deploy on Vercel — actively misleading given the real stack is Netlify + Railway.

### LOW (3 total)

No pre-commit hooks (no husky/lint-staged), pushing all feedback to CI which is itself largely non-blocking per the above; no `CODEOWNERS` file requiring review on the deploy-critical config files (`deploy.yml`, `railway.toml`, `netlify.toml`, `Dockerfile.worker`) that C1-C3/H2-H3 concern; no `.env.example` template committed, forcing reliance on the environment-variable table buried in `LYRA-Handover.md` (itself confirmed stale by Phase 3's H2 finding).

## Cross-phase synthesis

- **F1 (React `cache()`) and Phase 2's `connection_limit=1` finding compound each other directly** — the single highest-traffic code path in the app (dashboard navigation) currently issues avoidable duplicate DB writes onto an already-saturated connection pool. Fixing F1 alone would meaningfully reduce load on the exact bottleneck Phase 2 flagged as Critical.
- **H3 (unused Dockerfile) changes the practical urgency, not the correctness, of Phase 2's Docker-container Critical finding** — the root-as-user/leaked-`.env` vulnerability is real but currently dormant since Railway doesn't build from it. This should not be deprioritized, since H2 shows the repo's dead-code hygiene is poor enough that someone flipping `railway.toml` to use it without noticing the security gap is a real, not hypothetical, risk.
- **F3 (no `engines` field, inconsistent worker entrypoint) and H3 (Dockerfile not wired to Railway) are two views of the same underlying confusion**: it is not clear from the repository itself which of two different worker-start commands is authoritative. This should be resolved as one fix, not two.
- **H1 (npm test absent from CI) is now confirmed independently by three separate phases** (Phase 1 Code Quality C5, Phase 3 Testing T1, and this phase's CI/CD H1) — the highest-confidence, cheapest-to-fix finding in the entire review.
