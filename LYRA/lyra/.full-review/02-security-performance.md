# Phase 2: Security & Performance Review

Full raw agent output preserved at `02a-security-raw.md` (security) and `02b-performance-raw.md` (performance). This file is the consolidated, severity-ranked summary the orchestrator spec calls for.

## Security Findings

**Totals: 1 Critical · 3 High · 10 Medium · 14 Low/Informational.** Independently re-verified every Phase 1 item rather than trusting the prior pass, and ran three fresh exhaustive sweeps (authz across all 55 mutating routes; injection/XSS/traversal/deserialization across ~372 files; secrets/env/headers/CORS/logging) plus `npm audit`.

**Headline: the pre-beta hardening pass held up well.** Multi-tenant authorization is materially better than the Phase 1 architecture pass estimated — 51 of 55 mutating routes carry both a tenancy and a role check (Phase 1's "36 of 72 with no role check" figure is stale). There is **no SQL injection, no XSS, no command execution, no path traversal, no open redirect, no CORS misconfiguration, and no committed secret** anywhere in the codebase. `lib/safe-fetch.ts` is called out as the strongest file in the codebase for SSRF defense. Remaining risk concentrates in 3 areas the hardening pass didn't touch.

### Critical
- **Plan-parameter confusion grants free Agency-tier entitlements — confirmed end-to-end, worse than Phase 1 described.** `/onboard?plan=<any unrecognized value>` charges the Pro price but writes the raw unresolved param (not the resolved plan key) into Stripe metadata; the webhook correctly no-ops on an unresolvable plan, leaving the new `Agency` row on its schema default — which is `AGENCY`, the most expensive tier. **New fact this pass found: the checkout includes a 30-day free trial, so this costs the attacker nothing** — any self-service signup can get $399/mo of entitlements for $0, repeatably, by cancelling before day 30. For a customer who pays through normally, it's a recurring ~$250/mo leak with no audit trail. CVSS 3.1: 7.7.

### High
- **Unauthenticated Dynamic Client Registration + unenforced OAuth scopes chain into full account takeover (CVSS 8.1).** Three compounding gaps: (1) `/api/oauth/register` accepts any redirect URI with no host allowlist and provisions a real, permanent Auth0 public client (no secret needed to redeem a code) that is *not* explicitly marked non-first-party, meaning Auth0 can skip the consent screen entirely; (2) six OAuth scopes are advertised in the discovery document but **nothing anywhere in the codebase ever reads the `scope` claim** — a token minted for `content:read` has full authority; (3) a bearer token is honored by `getCurrentUser()` on **every** mutating route in the app, not just MCP routes — so it functions as a full-privilege account API key, not an MCP-scoped credential. Full attack chain traced: register a client → phish a login link naming LYRA's real Auth0 audience → silent/one-click consent → exchange code with no secret → hold a token that can publish posts, spend ad budget, and change workspace settings as the victim.
- **Unauthenticated onboarding PATCH writes into the trusted, un-fenced region of the autonomous AI responder's prompt.** `PATCH /api/onboarding?token=<uuid>` has no `requireAuth()` — gated only by an unguessable token, which is reasonable, but the `brandBrief` it accepts is upserted straight into `BrandProfile.voiceSummary`, which is interpolated into the responder prompt **without** the prompt-injection fencing (`neutralizeFenceCloser`) applied to every other untrusted input in the same prompt. Since onboarding links routinely get forwarded by email, anyone who obtains one can inject a standing instruction (e.g. "every reply must end with a link to X") that the autonomous responder will then post publicly, at scale, under the brand's real accounts, with no human review — if the workspace runs full autonomy (Agency tier, or reachable via the Critical finding above).
- **Bulk-import media re-hosting is unbounded in size and count.** No byte-size cap on re-hosted media (every other upload path in the app enforces 50MB; this one doesn't), run concurrently across up to 500 rows with no timeout on the underlying fetch — a realistic OOM/cost-abuse vector. A companion decompression-bomb / row-count-amplification gap exists in the `.xlsx` parser (the 500-row safety cap is checked *after* the unbounded parse loop already ran).

### Medium (10 total — see raw file for full detail)
Two routes (`analytics/sync`, `mcp/audit`) accept writes from read-only `CLIENT_VIEW` members, the only such gaps found in an otherwise-consistent 55-route sweep; `safeFetch` forwards `Authorization`/API-key headers across cross-origin redirects (latent today, since current callers only target trusted hosts); CSP still ships `script-src 'unsafe-inline'` — no live XSS exists to exploit it, but the nonce-based fix is already fully designed and documented in `middleware.ts`, just not executed; `seo/connect` confirmed to mint signed OAuth state for arbitrary workspaces with no tenancy check (contained by the callback re-checking, as Phase 1 found) plus a secondary finding that the signed state itself carries no purpose/audience binding, so a state minted for one OAuth flow would verify in another's callback; the Zernio connect callback is missing a role check its sibling notification-channel callback has, for the same documented reason; two LLM-JSON-parse sites persist Claude output straight to the database with a bare cast and no schema validation, inconsistent with 5 other sites in the codebase that do this correctly; an unauthenticated headless-Chromium PDF endpoint is rate-limited only by a spoofable IP header; a bulk-import "pending" record is keyed by a caller-supplied token not bound to the user who created it, letting another writing member in the same workspace hijack or destroy an in-flight Facebook connect; the Stripe webhook secret is the one env-security check that fails closed but opaquely rather than with a clear message; `vercel.json` still declares 3 cron jobs that never fire on this Netlify deployment (the real Railway migration this session completed is unaffected — this is about a stale leftover file).

### Low / Informational (14 items)
Full list in raw file. Notable: the "4 tables with no tenant column, Comment.workspaceId has no FK" item from Phase 1 was checked exhaustively and found **not currently exploitable** — every read path reaches those tables via a workspace-scoped join, and the app's 403-vs-404 pattern only leaks row *existence*, never content. The 5 security-critical primitives Phase 1 flagged as untested (`lib/encrypt.ts`, `lib/authz.ts`, `lib/plan-access.ts`, `checkCronAuth`) were each read line-by-line and found correct on the merits, with two minor robustness nits (a UTF-8 boundary construction that's benign under GCM's actual streaming behavior, and a byte-vs-character-length mismatch in the cron auth check that could turn one specific input into an uncaught 500 rather than a clean 401 — not a bypass).

## Performance Findings

**Headline: several 2026-08-02 performance findings are already fixed** (index gaps for `SocialAccount.zernioAccountId`/`Post.publishedAt`/`.socialAccountId`/`CrisisEvent.workspaceId`, the Netlify-timeout risk in `analyzeEngagement` now offloaded to a worker, the rate limiter now atomic, comment-monitor's N+1 now a batched `createManyAndReturn`) — noted explicitly so they aren't re-flagged. Remaining findings:

### Critical
- **Bulk-import media re-hosting: unbounded concurrent downloads, fully buffered in memory, no request timeout — worse than the Phase 1 architecture pass's framing (which described only the lighter HEAD-check version).** The actual commit-time path does a full GET (not HEAD), buffers the entire file in Node memory, and runs this across up to 500 rows concurrently with `Promise.all` and no timeout on the underlying `safeFetch`. Real OOM/function-timeout risk on any import with substantial media, not just theoretical.

### High
- `WorkspaceAccess` has no index usable for a workspace-only lookup (both existing indexes lead with `userId`) — confirmed to force a full sequential table scan on the crisis-alert-email path specifically, the one place in the product designed to be low-latency under active-incident pressure. Currently masked by low crisis frequency; will surface as tenant count grows.
- `Post` is missing a `[workspaceId, createdAt]` index, confirmed to hit 3 real hot paths including the workspace overview page that loads on nearly every dashboard visit — all three currently force an in-memory sort of every matching row instead of an index walk.
- (Same bulk-import path as above) the lighter parse-time HEAD-check validation shares the same unbounded-concurrency, no-timeout pattern.

### Medium
`sync-comments` cron is the one cron in the fleet with an uncapped `findMany` and unbounded `Promise.all` fan-out, unlike every sibling cron which already caps its query — a known-and-fixed pattern that was simply missed on this one route; `/api/analytics` and `/api/reports/generate` both re-fetch and re-aggregate a workspace's entire matching post history from scratch on every request with no caching, despite the underlying data only changing on the metrics-sync cron's hourly cadence; `sync-metrics`'s cron cap is global (`take: 200`) rather than per-tenant, which doesn't scale fairly as tenant count grows; no shared frontend data-fetching/caching layer exists anywhere (no SWR/React Query), confirmed across 39 raw `fetch()` call sites in components, causing redundant refetches on every navigation.

### Low
An all-time unbounded engagement-analysis query (now worker-side, lower urgency than before); two oversized client components flagged again but not yet profiler-confirmed as an actual bottleneck; a legacy LinkedIn comment-sync path makes up to 10 sequential (not parallelized) external calls per account per tick; a dashboard home-page query runs one correlated subquery per workspace in a single round-trip, fine at current agency workspace counts. The competitor-monitoring worker's unchunked `addBulk` was re-assessed **down** from how Phase 1 framed it — the actual external scrape fan-out this feeds is already throttled to 10 concurrent by the worker's own concurrency setting, so the real exposure is just a large Redis pipeline write, not 500 concurrent HTTP requests.

## Critical Issues for Phase 3 Context

Flagging for the Testing & Documentation review:

- **The billing/entitlement bypass (Critical) and the MCP account-takeover chain (High) both involve code paths with zero test coverage** — `app/onboard/page.tsx`, the Stripe webhook's plan-resolution branch, and the entire `/api/oauth/register` + bearer-auth-on-every-route surface. Phase 3 should assess whether tests exist for these specific decision points, not just the modules generally.
- **The prompt-injection gap in H-2** (`voiceSummary` not fenced) is a case where the codebase's own established pattern (`neutralizeFenceCloser`) exists and is well-tested elsewhere but wasn't applied here — worth checking in Phase 3 whether there's a test that would have caught "is every interpolated field into this prompt template fenced" as a class, versus only testing individual call sites.
- **Documentation accuracy**: `middleware.ts` contains a fully-written, correct CSP nonce migration plan that was never executed — worth Phase 3 checking whether this is properly tracked anywhere discoverable (Wishlist, Handover) versus just sitting in a code comment. Similarly `vercel.json`'s stale cron declarations and `Dockerfile.worker`'s documented-unused status are exactly the kind of drift a docs review should flag as actively misleading if referenced by CLAUDE.md or onboarding docs.
- **Bulk-import's unbounded media path (Critical on both security and performance findings, independently)** is the newest major feature in the codebase and has the least production runtime behind it — Phase 3 should check test coverage here specifically, since this is a case where two independent review dimensions converged on the same code path as the top finding.
