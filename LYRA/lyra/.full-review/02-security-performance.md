# Phase 2: Security & Performance Review

**Date:** 29 Jul 2026 · **Scope:** Full LYRA codebase, as defined in `00-scope.md`

---

## Security Findings

**Counts: 2 Critical · 9 High · 15 Medium · 11 Low**

### Executive summary

Application-layer security is substantially better than Phase 1's architecture review implied in places (clean injection surface, timing-safe secret comparisons everywhere, sound tenant-injection defenses in OAuth callbacks, a genuinely well-built prompt-injection mitigation in one AI call site) — but the real risk sits in four places Phase 1 didn't fully capture: a live secret sitting in an unprotected file inside a git repo whose root is the user's entire OneDrive folder; role-based access control enforced on only 4 of 66 routes (meaning the least-trusted role in the product, `CLIENT_VIEW`, can publish to a client's live social accounts and spend ad budget); 14 dependency advisories (10 High) with zero security scanning anywhere in CI; and the Phase 1 SSRF/plaintext-credential findings both confirmed exactly as described, with the SSRF actually worse than stated (it also runs inside the always-on Railway worker, not just a Netlify Lambda, and is reachable via an *unauthenticated* write path).

### CRITICAL

**C1 — Live Meta Graph API access token hardcoded in `scripts/meta-api-test.mjs`, in a file NOT covered by any `.gitignore` rule.** CWE-798, CVSS 10.0 (conditional on publication). The repo root is the user's entire OneDrive folder; a `git add -A` at that root would commit this token to the public GitHub remote. **Action needed immediately, independent of any code fix: revoke the token at developers.facebook.com.** Then move the value to an env var and add a pre-commit secret scanner (gitleaks/secretlint) so this class can't recur.

**C2 — The read-only `CLIENT_VIEW` role has full write/spend/delete capability on 62 of 66 routes.** CWE-269/863, CVSS 9.0. Role predicates exist in exactly 4 route files. A `CLIENT_VIEW` user — the role an agency grants its own client for review-only access — can `POST /api/posts/[id]/publish` directly (bypassing the approval workflow entirely), `POST /api/posts/[id]/boost` (spend real ad budget), `DELETE /api/guardrails/[id]` (silently disable Crisis Aware), and reply publicly as the brand. The correct pattern already exists in the codebase (`app/api/workspaces/[id]/route.ts`'s `OWNER_ROLES` check, added specifically to fix this exact bug class in one file) — it was never generalized to the other 62.

### HIGH (9 total)

- **H1** — SSRF: `services/brand-intelligence/scraper.ts` still runs a raw, unhardened `fetch()` for user-supplied website URLs, never adopting `lib/safe-fetch.ts` (which was explicitly extracted *from* this exact file to fix this exact bug). Confirmed worse than Phase 1's framing: it also runs inside the Railway worker container (private network reachability to Postgres/Redis), and `Workspace.websiteUrl` is settable via an **unauthenticated** onboarding-token endpoint. Response body is exfiltrated back through the UI (read-capable, not blind).
- **H2** — `EmailIntegration.apiKey` (full-access Klaviyo/Mailchimp/Customer.io keys) stored and read back in plaintext, while structurally identical `SocialAccount`/`SeoConnection` tokens correctly go through `lib/encrypt.ts`. GDPR Art. 32(1)(a) exposure.
- **H3** — 14 dependency advisories (10 High) via `npm audit`, zero security scanning of any kind in CI (no audit gate, no CodeQL, no Dependabot, no secret scanning); lint runs with `continue-on-error: true`; `npm test` never invoked in CI despite 37 passing tests existing. `next` is pinned below a patched version; `axios` and `sharp` both have unaddressed High advisories.
- **H4** — `.env` (42 live secrets) is copied into the Docker build context with no `.dockerignore`; worker container has no `USER` instruction and runs as root; base image is an unpinned floating tag.
- **H5** — Confirms the Crisis Aware entitlement bypass Phase 1 flagged, with a severity correction: CVSS scores it 4.3 (same-tenant, authenticated, revenue-only impact) — rated High here on business-risk grounds, not tenant-isolation grounds. Additionally found: cancelling the add-on or downgrading a plan **never revokes** `Workspace.crisisAware` or `aiResponseMode: 'FULL'` — a churned customer keeps the paid feature running indefinitely with no attacker required at all.
- **H6** — No rate limiting on the four most expensive routes in the product (`brand-intelligence/build`, `reports/generate`, `schedule/generate`, `comments/sync`) while the cheapest single-LLM-call routes are capped at 20/min — the limiting is inverted relative to actual cost.
- **H7** — `middleware.ts` excludes `/api` entirely from any framework-level auth backstop. This has already produced two real gaps: `app/api/seo/connect/route.ts` discards its own auth check result and performs no tenant validation at all (any authenticated user can mint a validly-signed OAuth state naming any workspace in the system); `upload/presign`'s tenant check is conditional on the client choosing to send a `workspaceId` field.
- **H8** — Presigned S3 uploads have no enforceable size limit: the size check is skipped entirely if the client omits the `size` field, and `getSignedUrl(PutObjectCommand)` cannot express a `content-length-range` condition regardless — the route's own comment claims to be "the actual gate" and is not. A second, worse instance (`guidelines/presigned`) has no size handling of any kind.
- **H9** — Rate limiting is bypassable by spoofing `x-forwarded-for` on the two unauthenticated routes that need it most (`help/pdf`, which launches headless Chromium per cache miss; `onboarding`, whose comment names the IP limit as the secondary defense against token brute-forcing). Netlify appends to this header rather than overwriting it, so the code's "leftmost element" logic reads attacker-controlled input; the correct trustworthy header (`x-nf-client-connection-ip`) is never referenced anywhere in the codebase.

### MEDIUM (15 total, headline items)

PKCE `code_verifier` transported unencrypted inside the OAuth `state` parameter on the Twitter connect flow (defeats PKCE's purpose against code interception); CSP's `script-src` includes `'unsafe-inline'` and `connect-src` allows any HTTPS host, removing CSP's value as an XSS containment layer; indirect prompt injection — scraped third-party website content reaches Claude with no fencing at 10 of 11 call sites (one call site, `response-generator.ts`, does this correctly with fencing + output re-validation, and that pattern was never generalized); the one existing fence delimiter isn't escaped, so a hostile comment body can close it early; any authenticated user can create unlimited workspaces and self-assign `AGENCY_ADMIN` with no plan-limit check; the public Klaviyo subscribe endpoint is fully unauthenticated and unrate-limited (list-poisoning/subscription-bomb vector); 4 routes (all on the plaintext-credential email-integration surface) have no try/catch at all, so an unauthenticated request gets a raw 500 instead of 401; 13 routes fetch-then-authorize in two round trips rather than one scoped query (not currently exploitable, but a one-line refactor hazard from becoming a real IDOR); zero structured logging/audit trail anywhere, so if C2 were exploited today there would be no way to detect or reconstruct it; Stripe webhook idempotency can permanently discard a billing event on a DB blip (bare catch treats any error, not just "already processed," as a duplicate-to-discard); the git repository root is the user's entire OneDrive folder containing personal/financial documents with no allowlist `.gitignore`, and separately produces a divergent duplicate of the whole app at the repo root that GitHub Actions actually reads instead of the `LYRA/lyra/` copy being edited; `CRON_SECRET` is interpolated directly into a shell command line in a GitHub Actions workflow rather than passed via `env:`.

### LOW (11 total, headline items)

Non-atomic rate limiter (INCR+EXPIRE as two round-trips — confirmed, but Low not Medium: blast radius is one bucket on a non-critical route); OAuth state-signing key falls back to reusing the session-encryption secret; OAuth state isn't bound to the initiating user/session; a byte-length-vs-string-length mismatch in the cron-auth timing-safe comparison could throw instead of returning 401 on a multibyte input; Redis traffic is unencrypted unless the connection URL happens to use `rediss://`, with no enforcement; no webhook replay protection (contained by idempotent upserts); a CLI scaffolding tool shipped as a production dependency; an env var naming mismatch (`AWS_S3_BUCKET` vs `.env`'s `S3_BUCKET_NAME`) that would fail at runtime with no boot-time validation to catch it early; inconsistent 403/404 use across routes leaks resource-existence information; `.env` (holding real values) is named like a template file, inviting an accidental unignore; the one cron route without `checkCronAuth` is currently harmless only because its handler is an unimplemented stub.

### Verification of all 7 Phase 1 security carry-overs

All seven were independently re-verified against source (not taken on faith): all seven confirmed real. Two severity corrections made with explicit reasoning: the Crisis Aware entitlement bypass was recalibrated from Phase 1's "Critical" to High/CVSS-Medium (same-tenant, authenticated, revenue-only — not a tenant-isolation breach); the missing role-gating finding was escalated to this report's #1 Critical (C2), since its real consequence is a full write/spend/delete grant to the least-trusted role in the product, not mere inconsistency. The non-atomic rate limiter was downgraded Medium→Low. The upload-size-limit gap was escalated Medium→High after confirming the server-side check is unconditionally bypassable, not just weak.

## Performance Findings

**Counts: 5 Critical · 7 High · 6 Medium · 3 Low**

### Executive summary

One important correction to a Phase 1 claim up front: "10 of 11 Claude call sites have no timeout" is out of date — `lib/anthropic.ts` was patched three weeks ago (commit `f471680`) to set a client-level 60s timeout that all 11 sites inherit. The real remaining gap is narrower (see F10). Otherwise, the two most consequential findings are architectural rather than single-query problems: the serverless app and the always-on Railway worker fleet share a single Postgres connection (`connection_limit=1`), which makes every worker's configured `concurrency: 5`/`concurrency: 10` decorative — real throughput is bottlenecked to one PgBouncer session regardless of how many jobs Node thinks are running in parallel; and the metrics-sync cron runs ~200 sequential external API calls inline inside a single serverless function invocation instead of through the BullMQ infrastructure that exists for exactly this pattern, which will very likely be killed mid-batch on any workspace with real publishing volume.

### CRITICAL

- **F1** — `sync-metrics` cron runs up to 200 sequential Zernio API calls + Prisma upserts, one at a time, inline in a single Netlify function with no worker offload and no `maxDuration` override — at 300-500ms per call this is 60-100+ seconds against a hosting platform's default timeout ceiling.
- **F2** — `SocialAccount.zernioAccountId` has no index despite being the sole predicate of two high-frequency webhook queries (every incoming comment, every disconnect event) — a full table scan that scales with total connected accounts across *all* customers, not just the relevant workspace.
- **F4** — No database migration system (same finding as Phase 1 Architecture C1, repeated here for its performance consequence specifically): with three unreconciled sources of truth for the live schema, there is no way to audit which indexes actually exist in production versus what `schema.prisma` declares.
- **F7** — The serverless app and the Railway worker fleet share one `connection_limit=1` pooled Postgres connection. All 15+ nominal concurrent BullMQ jobs across 5 workers serialize onto that single connection — configured worker concurrency is decorative under real load. This was flagged in the archived 18 Jul review as needing a second `DATABASE_URL` for the worker process; that has not happened.
- (A fifth Critical restates F1's `sync-metrics` finding from the connection-pooling angle — same root cause as F7, compounding it.)

### HIGH (7 total)

- **F3** — 13+ additional missing indexes on FK/filtered columns (`Post.publishedAt`, `Post.socialAccountId`, `CrisisEvent.workspaceId`, and others), currently latent given data volume but exactly the kind of drift the missing migration system makes invisible until a production slow-query alert.
- **F5** — `sync-metrics`/`analytics`/`reports`/`engagement-analyzer` all filter or sort on `Post.publishedAt` with no supporting composite index; the existing `[status, scheduledAt]` index doesn't match the actual query shape.
- **F8** — No graceful worker shutdown (`SIGTERM` calls `process.exit(0)` synchronously with zero drain) and no `.on('error', ...)` listener on any Queue/Worker — an unhandled BullMQ error event crashes the entire worker process, taking down all 5 workers simultaneously. Confirmed: nothing in the codebase ever re-checks a post stranded in `PUBLISHING` state after an interrupted deploy.
- **F9** — `Promise.all` (not `allSettled`) aborts whole batches on first rejection in two confirmed live spots: `comment-monitor.worker.ts`'s AI-response enqueue (comments already persisted before the fan-out — a mid-batch failure permanently orphans the remainder with no retry path) and the Crisis Aware email alert's multi-recipient send (one failed send silently drops the rest of the agency's admins from a safety-critical notification).
- **F12** — Same upload-size gap as Security H8, restated for its I/O-cost angle: unbounded uploads inflate S3 storage/egress cost independent of the security framing.
- **F18** — The missing workspace-creation entitlement check (Security M6) is also a scalability multiplier: unlimited workspace creation for one account turns bounded per-user dashboard queries into unbounded ones.
- (A seventh High covers the `getObjectBuffer` full-memory-buffering helper — safe today given its one caller, but a footgun with no size guard if reused for larger media.)

### MEDIUM (6 total, headline items)

Non-atomic rate limiter, restated from the performance-availability angle (a crash mid-INCR/EXPIRE permanently locks one user's bucket with no self-healing path); the LLM client's 60s default timeout exactly equals Netlify's own function ceiling with zero margin for post-call processing — one route (`schedule-generator.ts`) already lowered its own override to 45s specifically for this reason, and that fix was never generalized to the client default; no shared frontend data-fetching layer (68 raw `fetch()` calls, no request caching/deduplication — navigating away and back re-fetches everything from zero); analytics aggregation logic independently duplicated and recomputed fresh on every dashboard load and every PDF report with no caching, despite the underlying data being effectively immutable between metrics-sync cron runs; two oversized client components (`post-composer.tsx` at 14 `useState` hooks, `post-detail-panel.tsx` at 606 lines) with wide re-render surfaces, flagged as profiler candidates rather than confirmed via trace data; no structured logging/observability at all, meaning every finding in this report is otherwise invisible in production until a customer notices.

### LOW (3 total)

`help/pdf`'s existing S3-cache-plus-per-IP-rate-limit pattern is called out as a positive example worth protecting and replicating for analytics/reports; several previously-flagged frontend items (dynamic-imported charts, memoized list rows) were verified as already shipped and are not being re-flagged; comment ingestion's three independent implementations (also a Phase 1 finding) means platform-API backoff/rate-limit tuning has no single choke point if a platform starts throttling LYRA.

### Correction (post-review, 2 Aug 2026, verified during remediation)

**F7 ("app and Railway worker fleet share one `connection_limit=1` pooled Postgres connection") is not accurate as deployed.** Direct inspection of the live environments (`netlify env:get DATABASE_URL --context production` and `railway variables`) shows Railway's worker fleet has always had its own, separate `DATABASE_URL` — a direct (non-PgBouncer) connection on port 5432 with `connection_limit=10&pool_timeout=20` — genuinely distinct from Netlify's PgBouncer-pooled connection on port 6543. The `connection_limit=1` value only exists in the local `.env.local` file, which the review appears to have read as if it were representative of the deployed configuration rather than checking the real Railway/Netlify environment variables directly. Configured BullMQ worker concurrency (`concurrency: 5`/`10` per worker) is therefore not decorative — it has a real, appropriately-sized connection pool to use. `sync-metrics`'s inline-sequential-calls problem (the other half of F1/F7, no worker offload) was real and has been fixed separately (see `workers/metrics-sync.worker.ts`).

### Correction to Phase 1

The claim "10 of 11 Claude call sites have no timeout override" is superseded — verified via `git log` that `lib/anthropic.ts` already sets a client-level 60s timeout inherited by all 11 sites (fixed in commit `f471680`, predating this review). The real, narrower gap (F10 in the full agent output) is that only one of those 11 sites overrides the default down to a safer per-call value with margin below Netlify's hard ceiling — the recommended fix is a one-line change to the shared client default rather than 10 separate per-call patches.

## Critical Issues for Phase 3 Context

The following should inform the Testing & Documentation review:

1. **Zero test coverage on every file implicated in a Critical or High finding this phase.** The Stripe webhook (idempotency loss, entitlement checks), the publish state machine, `lib/authz`-equivalent logic (once built), the SSRF-vulnerable scraper, and the rate limiter all have no tests. Phase 1 already flagged this (C5); Phase 2 provides concrete evidence of *why* it matters — these are exactly the files where a 10-line test would have caught a real, currently-live vulnerability class.
2. **`npm test` is confirmed absent from CI** (both Phase 1 and both Phase 2 agents independently verified this against `.github/workflows/deploy.yml`) — Testing & Documentation review should treat "tests exist but don't run in CI" as itself a Critical/High finding, not just note the low coverage percentage.
3. **Help documentation accuracy is a live, recurring problem class**, independent of this technical review — cross-reference against the session's own recent work (`docs/LYRA-Demo-Reference-Guide.html` and multiple `components/lyra/help/*.tsx` sections were found this week to describe entirely fictional features: client self-service onboarding links, team member invitations with named roles, configurable notification preferences, an AI credit system). The Documentation review should treat every remaining unverified Help-doc claim as suspect until checked against actual code, not assumed accurate.
4. **The LYRA Trend billing situation** (Phase 1 Critical, both reviewers independently found it) has its own dedicated Help section (`section-13-trends.tsx`) describing the non-functional feature in full operational detail — this is a documentation-accuracy finding as much as a code one and should be scored/flagged again in Phase 3's documentation pass, not only in Phase 1's code quality pass.
5. **No `README.md` setup/deployment documentation was found or verified this phase** — Phase 3 should explicitly check whether one exists and is accurate, given the external cron-job.org dependency (Phase 1 H5) that isn't documented anywhere in the repository itself.
